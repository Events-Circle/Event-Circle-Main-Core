# Staging setup — prepared, not deployed

Target: Render Free for the NestJS Docker API, Supabase PostgreSQL and a **private** Supabase Storage bucket. Keep the existing Core auth; do not add a second Supabase user identity system. All application tables are reached through NestJS, never through the mobile/web client or Supabase's public Data API. The privacy migration enables row-level security without browser policies and revokes PUBLIC/anon/authenticated access on every application table. Also disable the Data API for this project or remove application tables from its exposed schemas. The backend connection must use the table owner or a deliberately configured server role that bypasses RLS; never a browser role. Keep service-role/storage credentials server-only.

1. Create a dedicated staging Supabase project and private bucket. Pick the same/nearby region as the API. Use staging test data only. Configure DB access through an appropriate IPv4-compatible session-pooler connection with TLS and a small Prisma connection limit; validate migrate deploy against this connection before enabling the app. Do not use a transaction-pooler connection for migrations.
2. Generate one persistent Ed25519 signing-key pair using the repository's key script and save the PEM values in Render secret environment settings. Do not commit keys or generate new keys on restarts. Existing keys on a deployment require deliberate rotation, not replacement by this template.
3. Create the Render Blueprint from `render.yaml`; it defines one Free Docker web service and **no billable database/worker**. Auto-deploy is off. Supply DATABASE_URL, JWT_PRIVATE_KEY_PEM, JWT_PUBLIC_KEY_PEM, HTTPS JWT_ISSUER, CORS_ORIGINS, PUBLIC_WEB_URL, STORAGE_URL, STORAGE_KEY and STORAGE_BUCKET. Use the Supabase project URL without a trailing slash. The Blueprint passed validation against Render's official JSON Schema; also validate it in the connected Render account before provisioning. No account was available to verify a live Blueprint deployment here.
4. The staging-only start script writes secret PEMs to protected temporary files, applies committed additive migrations and starts NestJS. It refuses to run without APP_STAGE=staging. Test migrations against a copy/backed-up database before adopting this command on existing data. Do not use this template as production migration orchestration.
5. Check `/api/v1/core/health/ready`, register two test suppliers, upload a real image, publish one profile, test public reads and inquiry receipt, then restart the service and confirm data persists. The API's temporary filesystem is never media storage.
6. Set the frontend's public API base URL to the HTTPS API origin. The URL is public configuration; database/password/storage/JWT signing secrets never go into EXPO_PUBLIC variables. Configure `/p/:slug` in the future website to match share links. Initially generated share URLs point at this planned route; they cannot be live until that website is deployed.

Render Free sleeps after idle time; cold requests can take roughly a minute. Its in-process workers do not run while sleeping. OUTBOX_WORKER_ENABLED stays false until actual idempotent consumers are installed. Supabase Free has storage/database quotas and inactivity pausing. This setup does not claim always-on production availability; add client startup/retry UX and a budget before production. Back up test data explicitly because free tiers have limited backup coverage.

Do not set blanket proxy trust to fix rate limiting. Configure only verified ingress proxy addresses using TRUST_PROXY_CIDRS; the template leaves trust disabled and therefore conservatively shares limits behind the proxy until the deployment's forwarding topology is verified.

## Mobile testing

The current shell targets Android and iOS and CI exports both bundles. The future frontend app should use an EAS **preview/internal distribution build** with the JS bundle embedded, not require a development server. Test Android first. Add real application identifiers, Expo project ID and signing in that frontend repo rather than inventing them in Main Core. iOS internal distribution requires Apple membership and registered devices; the user will provide that account later. No native iOS build or real-device compatibility is claimed by JS export.
